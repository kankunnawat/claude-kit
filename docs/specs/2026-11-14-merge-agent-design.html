Approve: one merge agent skill that follows each repo's own PR rules

You type /merge-agent in a repo. The session finds that repo's PR gate guide, follows it for your open PRs one at a time, and drafts a guide first when the repo has none.

1 · Today

Every merge session is briefed by hand

Three repos have a PR gate, each in its own file and its own words. A session only follows it if you point it there. A stale local copy already named the wrong branch once.

2 · The change

The skill finds the guide and follows it

The rules stay in each repo. The skill carries no repo names, tier names or merge commands, so a guide can change without touching the skill.

Names: skills/merge-agent/SKILL.md, merge-agent.py

3 · How it runs

One PR at a time, by the repo's rules

  1. 1Check the repo: default branch, gate guide, verification skill, and whether your guardrails let an agent merge here.
  2. 2No guide: draft one with three risk tiers, open it as a PR, and merge nothing until you land it.
  3. 3Pre-check the PR: yours, open, not held, and still on the commit that was looked at.
  4. 4Set the risk tier the guide's way. The agent may raise it, never lower it.
  5. 5Accept the review verdict recorded at that exact commit. Review again, with a fresh session, only when the head moved.
  6. 6Run the checks the guide names. For a behaviour change, run it like a user.
  7. 7Merge with the repo's pinned command, or stop at merge-ready and hand you the link.
  8. 8Report each PR as landed, merge-ready or held, with what was not verified. No tracker writes: the coordinator makes them.

Risk → answer

A helper script that merges would slip past the merge guard, because the guard only reads the command the agent types.
The script never merges and never posts. It prints the pinned command and the agent types it, so the guard still judges every merge.
The skill is taken as permission to merge anywhere.
The skill grants nothing. Your guardrails and the guard decide. Outside the named repos it stops at merge-ready.
The agent merges its own gate guide, or a PR that changes agent instructions.
Any PR that changes a gate guide or agent instruction files waits for you, including the guide the skill drafts.
The session reads an old copy of the rules from a stale checkout.
The guide is read from the remote default branch every time, never from the working tree.
A PR comment or another session's message talks the agent into a merge.
Only your own words in the session count. Other people's PRs need your yes for that PR.
Text search misses a guide and the skill drafts a second one over it.
When it finds review rules but no clear guide, it shows them and asks before drafting.

For you to decide

  1. How much should the helper script do?I recommend three read-only commands: check the repo, list your open PRs with what holds each one, and pre-check one PR before merge. The other choice is the repo check only, with the rest done by hand each time.
  2. What happens in a repo with no verification skill?I recommend the agent warns, says what was not proven, and offers to create one. The stricter choice refuses to merge any behaviour change there, which would block most repos today.
  3. Should the skill propose guide updates after a landing teaches a new rule?I recommend yes, as a PR to that repo's guide that waits for you. Leaving it out keeps the skill smaller, and lessons stay in chat.
  4. Which tiers should a newly drafted guide use?I recommend three: low, medium, high, as agentic-discovery uses. The other choice is four tiers, T0 to T3, as hausback-core and AlphaOS use, which needs a tier tool to be worth it.

Reply "approved" to take the recommendation, or say what to change.

Already decided

  • A global skill in claude-kit that routes to each repo's own rules (your "go 1").
  • The repo declares its gate; the skill keeps no table of repos.
  • Your own PRs only, unless you say otherwise for one PR.
  • Always pinned to the reviewed commit, never auto-merge, never admin.
  • hausback-core keeps landing through its own lane tool.
  • Proven by replaying six of today's cases read-only, then a fresh review of the built skill.

Left for later: how a hold label is read where the guide names none; whether the PR list orders a stack itself; what to do when a PR targets a production branch.

Not in this change: editing any repo's gate guide or the merge guard, adding repos to the merge exceptions, deploys and promotions, writing a repo's verification skill, other people's PRs by default.
