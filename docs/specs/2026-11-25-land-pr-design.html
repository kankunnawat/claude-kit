Approve: one verb, /land-pr, takes an open PR through review and fixes to merge-ready

It follows the repo's own PR gate where one is declared, and runs one fresh review plus one check of the fixes everywhere else.

1 · Today

Work stops when the PR opens

Every piece of the review loop exists, but no verb starts from an open PR and runs them in order. Each repo needs a different one.

The worktree is gone before the first finding arrives, so each fix begins by rebuilding it.

2 · The change

One verb runs the middle, cleanup moves last

The reviewer is always a session that did not write the change. The skill grants no merge right: your guardrails and the merge guard still decide.

Names: skills/land-pr/SKILL.md, reusing merge-agent.py doctor and precheck

3 · How it runs

Nine steps, three ways in

  1. 1Find the PR. Rebuild the worktree from the kept branch if it is gone.
  2. 2Check the repo. It declares a gate: follow it with its own tools. It declares none: run the built-in loop. Not on GitHub: print the repo's own command for you and stop.
  3. 3Round 1: one fresh review of the whole PR, plus CI and bot findings.
  4. 4Label every finding Fix, Note or Dismiss. Only Fix changes code.
  5. 5Commit the fixes, then one fresh review of the fix commits. No round 3.
  6. 6Run tests and wait for green CI on the final commit.
  7. 7Post the verdict. It names the last commit a reviewer read, so a later commit means "not yet".
  8. 8Merge where your guardrails allow it, pinned to that commit. Otherwise hand you the command.
  9. 9Close with /finish: tracker, worktree, daily log.

Risk → answer

The session reviews its own fixes and passes them.
Every review comes from a fresh session that gets only the diff range and the commit. Where a repo forbids the author to sign, the skill posts no verdict.
The loop never ends, and the PR grows one small fix at a time.
One review of the fix commits, no round 3. Only confirmed bugs change code; the rest is listed as a note.
A fix lands after the last review and merges unread.
The verdict names the last commit a reviewer read. Any later commit makes it "not yet".
It merges somewhere an agent should not.
It types the same pinned command the merge guard already judges, and stops at merge-ready when the guardrails do not name the repo.
Worktrees stay longer and fill the disk again.
/land-pr runs in the same session right after the PR opens, and /finish still removes the worktree at the end.
It overrides a repo's own gate.
A declared gate wins on every point. The round cap applies only where the repo sets none.

For you to decide

  1. In a solo repo with no gate of its own, does it merge the PR after a pass, or stop at merge-ready?I recommend it merges: your solo-repo rule already lets an agent merge its own PR after an independent review and green tests, and stopping would leave the last step to you every time.
  2. Does the worktree get removed at the merge, or as soon as the verdict is a pass?I recommend at the merge: a change you ask for while reading the PR then has its worktree ready. The cost is that a PR waiting on you keeps its worktree on disk until you merge it.

Reply "approved" to take the recommendation, or say what to change.

Already decided

  • A new skill, not a fold into /finish or merge-agent.
  • The name is land-pr, since pr-gate is taken by a repo's own skill.
  • One round of fixes, then one review of those fixes.
  • No repo's gate, tier rule or verdict format changes.

Left for later: what the author's session does in hausback while it waits for a signer; a bot finding that arrives after round 2; whether a repo with review rules but no gate guide should stop and ask.

Not in this change: tier rules for repos that have none, releases and deploys, stacked PRs, a queue of PRs, other people's PRs.
